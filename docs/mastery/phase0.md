# Phase 0 — Mastery Log

This is not a completion tracker — `phase0/README.md` already does that (sections/projects done or not). This is a separate, honest record of how *deeply* the load-bearing concepts inside those completed sections actually landed, backed by specific evidence rather than "the exercise is checked off." Completing an exercise and understanding it are different facts; this file is where that difference gets written down instead of silently assumed.

Not every concept in Phase 0 gets an entry — only ones that later phases genuinely depend on, or ones where the real difficulty of learning them turned out to be a useful signal.

## Scale

`Exposed` → `Practiced` → `Understood` → `Implemented` → `Applied` → `Verified` → `Mastered`

- **Exposed** — read about it, hasn't been exercised yet.
- **Practiced** — attempted it, needed significant hints or scaffolding to get through it.
- **Understood** — can restate the idea in different words, ideally without prompting.
- **Implemented** — working code exists and passes its tests.
- **Applied** — used inside a larger project, not just an isolated exercise.
- **Verified** — checked against an independent method (finite-difference gradient check, a known closed-form answer, etc.), not just "it ran without error."
- **Mastered** — several of the above, sustained across more than one context, without help.

Most entries below sit in the middle of this scale. That's expected for Phase 0 — it's the honest state, not a problem to hide.

## Project 3 — Linear Regression from Scratch (complete, 2026-09-11)

- **Linear regression as `y = Xw + b`** — *Understood*, 2026-09-05. Initially explained (wrongly) via assumed econometrics background; rebuilt from plain slope/intercept algebra (`y = mx + c`) once that assumption was corrected. Could then correctly restate what `w` and `b` represent, but a follow-up mistake (`score` calling `r_squared(X, y)` directly instead of predicting first) shows the model/metric boundary isn't fully solid yet.
- **Closed-form OLS via `np.linalg.lstsq` + augmented-ones trick** — *Verified*, 2026-09-05. Implemented, then confirmed by recovering exactly known `w = [2, -1]`, `b = 3.0` from synthetic data with `score() == 1.0`, after two real bugs were found and fixed (`X[0]` used instead of `X.shape[0]`; non-idiomatic `rcond=False` instead of `rcond=None`).
- **Method chaining (`return self`)** — *Implemented*, 2026-09-05. Unfamiliar pattern; understood immediately once shown a working-vs-broken comparison, then applied correctly in `fit()` without further correction needed.
- **Batch and mini-batch gradient descent** — *Verified*, 2026-09-06/09. Needed a full ground-up rebuild of what to assign to `self.w`/`self.b` and how the MSE gradient chains through `d_out → grad_w`, plus fixing a silent dispatch bug (`elif self.method == "closed"` never matched `"closed_form"`, leaving `w`/`b` as `None` with no error). Mini-batch introduced a real conceptual bug — sliced `self.w`/`self.b` by batch position instead of `X`/`y` (parameters have no per-sample axis) — caught via `TypeError` and corrected. Verified by recovering known synthetic weights within tolerance and by explaining *why* mini-batch's loss curve looks different from batch's, not just that it does.
- **L2 (ridge) regularization** — *Applied*, 2026-09-09. Correctly added `2 * alpha * w` to `grad_w` only (never `grad_b`), verified via an explicit test: ridge's recovered weights on collinear synthetic features have smaller total magnitude than the unregularized fit (assertion passes). Still needed the collinear-feature construction (`hstack` with a near-duplicate column) and the interpretation of `alpha` walked through explicitly — not self-generated first.
- **Momentum and Adam optimizers** — *Verified*, 2026-09-09. Both `momentum_step` and `adam_step` shipped with the identical real bug on first attempt — returning a single array instead of the tuple their own type hints promised, breaking state carryover between calls (`ValueError: not enough values to unpack`) — caught via execution, explained once, then self-corrected the second time without the same mistake recurring. Verified against a noisy toy function (`f(x,y) = x² + 5y²`, matching `math_concepts.md` 1.2's worked example): momentum outperforms vanilla under matched noise, and adaptive-step behavior was independently confirmed once wired into `_fit_gd`'s dispatch (state initialized once outside the epoch loop, not reset per-epoch — a real design point, not just syntax).
- **Optimizer comparison under noisy gradients** — *Understood*, 2026-09-11. Initially unsure whether the loss trending toward zero was a bug ("are they distorting the result?") — corrected to recognize convergence-to-minimum as the intended behavior being measured, not an artifact. Went on to find and correctly explain a genuine, non-obvious empirical result on the actual toy-function run: with a shared learning rate tuned for vanilla GD, Adam converges markedly slower (final loss `9.7` vs. vanilla's `0.14` at matched `lr=0.02`) since its normalized per-parameter step doesn't exploit the large early gradient the way vanilla/momentum do — directly contradicting a naive "Adam always wins" assumption, which is exactly what `projects.md`'s note on this step warns against assuming.
- **Feature standardization (z-score)** — *Verified*, 2026-09-10/11. First attempt computed `X.mean()`/`X.std()` with no `axis`, collapsing all features into one shared scalar instead of per-feature statistics — caught in review before running. Corrected version (`axis=0`) produced California Housing R² of `0.6013`, landing inside the spec's expected 0.5-0.7 band on the first working run.

## Project 4 — NumPy Neural Network (complete, 2026-09-23)

- **Weight initialization (small random vs. zero, symmetry breaking)** — *Understood*, 2026-09-12. Explained and applied correctly (`randn * 0.01` for `W1`/`W2`, zeros for `b1`/`b2`) on first attempt, no bugs. Not yet pushed on with a "what if both were zero" follow-up, so treat as explained-and-applied rather than independently reasoned-through.
- **Backpropagation through two stacked layers (the chain rule, applied twice)** — *Verified*, 2026-09-12/22. This was the real test of the phase. First attempt at `backward` skipped the chain entirely (`W1 = X.T @ z1`, no use of the loss or `d_logits` at all) and the abstract matrix-formula explanation didn't land — explicitly said "I don't know if I even feel confident with the basics" when asked to derive `dW2`. Paused mid-project to watch 3Blue1Brown's "Backpropagation calculus" and the start of Karpathy's micrograd lecture before returning. Second pass, rebuilt from a fully worked concrete numeric example (2 features, 2 hidden units, 1 sample, real numbers throughout) plus a live finite-difference check, landed correctly: `dW1`, `db1`, `dW2`, `db2` all implemented right on the next attempt, and the model's own `gradient_check` method — built afterward, independently — confirmed all four relative errors around `1e-9`, several orders of magnitude under the spec's `1e-4` bar. The external-resource detour was necessary, not a shortcut; worth remembering this concept needs more than one explanation style to land.
- **`relu_backward` (gradient masking)** — *Verified*, 2026-09-12. First attempt (`np.maximum(dout, 0)`) clamped based on the sign of the incoming gradient instead of the sign of the original input — caught with two concrete counterexamples showing it wrong in both directions. Second attempt (`np.where(x >= 0, dout, 0)`) correct immediately, then confirmed against the same counterexamples.
- **Numerical gradient checking, extended to a whole network's parameters** — *Verified*, 2026-09-12. Reuses the finite-difference idea from NumPy Section 8, now looped over every parameter array via `np.nditer`. Real bugs on first attempt: looped over `cache.keys()` instead of the actual parameter names (`getattr(self, "X")` doesn't exist), a `np.lialg.norm` typo, and a missing `return` — same "function computes the right thing but never returns it" mistake as `backward` made a step earlier. All three fixed and the resulting `gradient_check` method is now the project's actual proof of correctness, not just a one-off manual check.
- **Mini-batch SGD training loop, with per-epoch shuffling** — *Verified*, 2026-09-22. Mostly direct reuse of Project 3's `_fit_gd` batch-slicing pattern; the genuinely new piece (shuffling indices fresh each epoch) was applied correctly once explained. Bugs on first attempt: no outer epoch loop at all (`n_epochs` unused), comma instead of colon in the batch slice (`X_shuffled[batch, batch+batch_size]`, valid but wrong NumPy syntax), and `y_batch` built from `X_shuffled` instead of `y_shuffled`. A later, subtler bug — `(preds == y_val.mean())` instead of `(preds == y_val).mean()`, comparing predictions to the *average* label instead of averaging the correctness array — was caught before running rather than after, a good sign for reading code for what it actually does rather than what it looks like it does.
- **Learning-rate instability, found empirically** — *Applied*, 2026-09-23. `train()`'s spec-default `lr=0.5` produced a loss curve that dropped for ~8 epochs then rose sharply, ending higher than it started. Diagnosed correctly and independently as overshoot near the minimum (large steps that helped early become destabilizing once the loss surface narrows), without being told what the cause was first — just asked "why does train loss suddenly rise?" and was walked through comparing `lr=0.5/0.1/0.05` side by side. This is the same phenomenon as Project 3's optimizer-comparison lr-mismatch finding, showing up unprompted in a new context — the kind of transfer this log exists to notice.
